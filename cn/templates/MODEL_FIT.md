# 模型档位适配指南与通用失效对策（Model Fit）

> 为什么不能用一套几十 KB 的铁律去要求所有模型？  
> 因为在指令密度过高或上下文深处，**越轻量或依赖特定推理路径的模型，越容易出现“规则瘫痪”或静默丢约束**。

---

## 一、快速选型表

| 模型档位 / 典型特征 | 推荐模板 | 规则上限建议 | 避坑重点 |
|---|---|---|---|
| **轻量 / 高速 / 性价比模型**<br>例：`DeepSeek-V4.1-Flash`、`Gemini Flash`、`Claude Haiku`、`GPT-mini` | `AGENTS.lite.md`（`~2.0 KB` / 12 行） | `≤ 15` 条核心规则，优先正向表述 | **严禁注入长篇写作规范与复杂格式要求**；所有收尾验收交给外部脚本，不靠模型自己写自检报告。 |
| **旗舰通用 / 深度推理模型**<br>例：`Claude Opus / Sonnet`、`Gemini Pro`、`GPT` 旗舰 | `AGENTS.lite.md`（日常）<br>`AGENTS.strict.md`（审计/大重构） | 根文件保持在 `≤ 80` 行，细节按需去 `handbook/` 读 | 依然警惕“过度服从陷阱”——避免把项目目录树和废话写进 `AGENTS.md`，浪费 Token 与推理步数。 |

## 二、通用 Agent 失效症状 → 工程对策表（跨模型适用）

无论你用的是哪家大模型，长对话写代码时遇到以下 5 类高发症状，都可以直接套用对应解法：

| 常见症状（黑盒表现） | 典型触发条件 | 通用工程对策 |
|---|---|---|
| **1. “嘴上开工、实际零动作”**<br>回复“我接下来会检查并修改 X 文件”，但对话直接结束、磁盘零变更 | 深上下文（如 `≥ 80K tokens`）+ 高思考强度 | 拆短会话；凡模型回复承诺性语句，用 `git status` 或脚本核对磁盘是否真的有改动；必要时降低思考档位。 |
| **2. “思考烧干 / 吞掉正文”**<br>内部思考占满输出上限，结果正文截断或空白 | 单轮下发“全面研究并一次吐出完整方案”类开放指令 | 把大任务拆成带明确交付格式的小步；用外部脚本校验返回字段，不靠肉眼猜它有没有说完。 |
| **3. “工具标记直接漏在正文里”**<br>聊天框打印出原始工具调用标签/JSON，但工具并未真正执行 | 工具 schema 过长、上下文杂乱或模型格式退化 | 立即新开干净短会话，减少当轮同时挂载的无用工具数量。 |
| **4. “虚假上下文已满预警”**<br>刚压缩完上下文，模型自己慌称“窗口快满了”拒绝继续 | 模型看不到宿主真实剩余 Token 账单，读到长日志产生误判 | 以宿主/CLI 实际 Token 统计为准；但实践上仍建议在 **120K–160K tokens** 前主动换新会话防注意力退化。 |
| **5. “长对话越聊越忘规矩”**<br>前几轮读过的规则在中段被静默丢弃（Context Rot） | 会话拉扯超过 15–20 轮或塞满报错日志 | **信息搬近 + 状态外置**：别骂它“重读前面第 X 条”，把当下这步最关键的 1–2 条限制直接贴在**本轮指令末尾**，进度写进盘上小清单。 |

## 三、实测案例：`DeepSeek-V4.1-Flash` + `reasoningEffort: max`

在长期高强度 Agent 协同实战中，曾针对 `DeepSeek-V4.1-Flash` 搭配高思考强度（`reasoningEffort: max`）做过专门踩坑追踪，上面表格的症状正来源于此处的 5 类实测失效边界（内部编号 `M1–M5`）：
- **路由与定位**：部分 API 网关会将别名（如 `deepseek-v4-pro`）统一路由到 `V4.1-Flash` 底层。把它定位为**“按明确清单执行局部脚本、清洗与跑测的执行型助手”**极佳，不适合在长对话里单扛跨文件全局架构决策。
- **典型签名**：`M1`（`finish_reason=stop` 且 `tool_calls` 为空，宣布开工却零动作）、`M2`（`reasoning_content` 烧干导致 `finish_reason=length`）、`M3`（正文为空直接 `stop`）、`M4`（误报上下文快满）、`M5`（正文泄漏 `<｜DSML｜>` 原始标记）。

## 四、给小白的终极口诀

> **大活分步切短会话，弱模只配 Lite 规则；  
> 思考卡壳别硬等，检查磁盘最诚实；  
> 真正危险的操作，交给 Git 和宿主审批，别指望模型自觉。**
